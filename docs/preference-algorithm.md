# 好み分析・レコメンド アルゴリズム仕様

要件定義 5.7 / 5.8 の実装仕様。

---

## 0. 設計思想

本アプリの核心価値は「自分の好みを客観化できること」であり、その信頼性は
**推薦精度そのものよりも「なぜそう判定されたかが説明できること」**に依存する。

したがって v1 では、精度で勝る可能性のあるブラックボックス手法（行列分解・埋め込みベース）を採らず、
**すべての判定に根拠となるログを提示できる統計的手法**を採用する。

また、課題として挙げられている
「同じローズでも配合バランスによって好き嫌いが分かれる」問題に対しては、
単一香料だけでなく **香調アコード** と **香料の共起ペア** を併せて特徴量とすることで対応する。

---

## 1. 用語と記号

| 記号 | 意味 |
|---|---|
| `u` | ユーザー |
| `n` | 香料（note） |
| `a` | 香調アコード（accord） |
| `r_i` | ユーザーのログ *i* の評価（1.0〜5.0、0.1 刻み） |
| `μ_u` | ユーザー `u` の全評価の平均 |
| `N(u,n)` | ユーザー `u` が評価した香水のうち、香料 `n` を含むログの件数 |

同一香水に複数回ログがある場合は、**香水ごとに平均をとって 1 件として扱う**
（何度も試した香水が過剰に重み付けされるのを防ぐ）。

---

## 2. Step 1 — ベイズ平均による件数バイアス補正

単純平均だと「1 回だけ高評価だった香料」が上位を独占する。
ユーザー自身の平均評価を事前分布として、サンプル数の少ない香料を中央へ引き戻す。

```
raw_score(u, n) = (C * μ_u + Σ_{i ∈ logs(u,n)} r_i) / (C + N(u,n))
```

- `C = 3`（事前サンプル数。チューニング対象。初期値は経験則）
- `N(u,n)` が小さいほど `μ_u` に近づき、大きいほど実測平均に近づく

---

## 3. Step 2 — センタリング

ユーザーごとの採点の甘辛を除去する。

```
preference(u, n) = raw_score(u, n) - μ_u
```

- `preference > 0` → 好きな傾向
- `preference < 0` → 苦手な傾向

香調アコード `a` についても、まったく同じ式で `preference(u, a)` を算出する。

---

## 4. Step 3 — 表示閾値と信頼度

| 条件 | 扱い |
|---|---|
| `N(u,n) < 3` | ダッシュボードに表示しない（内部計算には使う） |
| `3 ≤ N(u,n) < 5` | 「参考」ラベル付きで表示 |
| `N(u,n) ≥ 5` | 通常表示 |

**UI では必ずサンプル件数を併記する**（例:「ベルガモット — 好き（8 件のログに基づく）」）。
根拠となったログ一覧へドリルダウンできること。

**分析開始の閾値**: ユーザーの総ログ件数が **10 件**に達するまでダッシュボードは
「あと N 件で分析が始まります」という進捗表示にする。
それまではオンボーディングで選択した香調を暫定プロファイルとして使う。

---

## 5. Step 4 — 配合バランス問題への対処（共起ペア）

「ローズは平均的に好きだが、ローズ×ウードの組み合わせは低評価」といった
条件付きの傾向を捉えるため、香料の共起ペアを特徴量に加える。

### 対象ペアの絞り込み

全ペアを計算すると組み合わせ爆発を起こすため、以下で絞る。

1. そのユーザーのログに **3 回以上共起している**ペアのみ
2. 各ログの香料は `position_order` 上位（＝主要な香料）に限定する
   （すべての微量成分を対象にするとノイズになる）

### スコア

```
preference(u, n_a, n_b) = raw_score(u, {n_a, n_b}) - μ_u
```

### 提示条件

ペア単体のスコアではなく、**構成香料単体のスコアからの乖離**が大きいときのみ提示する。

```
interaction = preference(u, n_a, n_b) - (preference(u, n_a) + preference(u, n_b)) / 2
```

`|interaction| ≥ 0.5` かつ共起件数 ≥ 3 のときに、
「ローズ系は好きですが、ウードと組み合わさると評価が下がる傾向があります」のような
文言テンプレートで提示する。

---

## 6. Step 5 — レコメンド

### 6.1 ユーザー嗜好ベクトル

香料と香調を連結した疎ベクトル `P_u` を作る。

```
P_u[n] = preference(u, n) * confidence(N(u,n))
P_u[a] = preference(u, a) * confidence(N(u,a)) * w_accord
```

- `confidence(N) = N / (N + C)` — サンプルが少ない次元の影響を抑える
- `w_accord = 1.5` — 香調は香水全体の性格を表すため、香料より重みを置く（チューニング対象）

### 6.2 香水ベクトル

```
V_p[n] = position_weight(position) * order_weight(position_order)
V_p[a] = strength(a) * w_accord
```

`position_weight`: `top = 0.8`, `middle = 1.0`, `base = 1.0`, `unspecified = 0.6`
（トップノートは揮発が早く、評価への寄与が相対的に小さいという前提）

`order_weight`: 記載順 *k* に対し `1 / (1 + 0.15 * (k - 1))`

### 6.3 スコアリング

```
base_score(u, p)  = cosine(P_u, V_p)
penalty(u, p)     = Σ_{n ∈ p, preference(u,n) < -T} |preference(u, n)| * confidence(N(u,n))
pair_adjust(u, p) = Σ_{(a,b) ∈ pairs(p)} interaction(u, a, b)

score(u, p) = base_score(u, p) - λ * penalty(u, p) + γ * pair_adjust(u, p)
```

- `T = 0.3`（苦手判定の閾値）
- `λ = 0.4`, `γ = 0.2`（チューニング対象）

### 6.4 出力の要件

- 既に試香ログがある香水は除外する
- スコア上位から提示するが、**推薦理由を必ず添える**
  - 加点の主因となった香料・香調を上位 2 件抽出して文章化する
  - `penalty > 0` の場合は「苦手な◯◯を含みます」と警告を併記する
- 多様性の確保: 同一ブランドが上位に連続しないよう、
  上位 20 件からブランドごとに最大 2 件へ間引いて最終的に 10 件を提示する

### 6.5 コールドスタート

ログ 10 件未満のユーザーには、
オンボーディングで選択した香調・ブランドから `P_u` を暫定生成して推薦する。
この場合 UI 上で「あなたが選んだ好みに基づく仮の提案です」と明示する。

---

## 7. 好み適合度（香水詳細に表示するスコア）

```
match_rate(u, p) = clamp(0, 100, round(50 + 50 * score(u, p)))
```

- `is_analysis_ready = false` のユーザーには表示しない
- 「87% 一致」のような断定的な数値の下に、必ず根拠（寄与した香料）を併記する

---

## 8. 実行タイミングと保存

1. 試香ログの作成・更新・削除時に、対象ユーザーを再計算キューへ入れる
2. Supabase Edge Function（または pg_cron）が再計算を実行
3. 結果を `user_note_scores` / `user_accord_scores` / `user_note_pair_scores` /
   `user_profile_state` へ upsert
4. レコメンドはリクエスト時に、キャッシュ済みの `P_u` と香水ベクトルから計算する
   （香水数が数万件規模になるまでは、Postgres 上の計算で十分）

**リアルタイム集計はしない。** ログ保存の応答速度を優先し、分析は非同期で更新する。
更新完了までは前回の分析結果を表示し、UI に「更新中」を出す。

---

## 9. 評価とチューニング

v1 リリース後に以下を計測し、パラメータ（`C`, `w_accord`, `λ`, `γ`, `T`）を調整する。

| 指標 | 測り方 |
|---|---|
| レコメンド納得度 | 推薦カードへの「これは好みじゃない」フィードバックボタンの押下率 |
| 分析の的中率 | 推薦経由でログを付けた香水の評価が `μ_u` を上回る割合 |
| 分析到達率 | サインアップから 10 件のログに到達したユーザーの割合 |

**「これは好みじゃない」フィードバックは v1 から実装する。**
チューニングの唯一の教師信号になるため、後回しにしない。
