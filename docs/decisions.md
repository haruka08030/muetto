# 意思決定ログ (ADR)

要件定義フェーズで確定した判断と、その理由。
後から「なぜこうなっているのか」を追えるようにするための記録。

---

## ADR-001: 既存コードをすべて削除する

**決定**: `x-to-notion`（X→Notion 保存 Chrome 拡張）のコードをすべて削除し、
同一リポジトリを香水管理アプリとして作り直す。

**理由**: 技術スタック・目的ともに共通点がないため。Git 履歴は残す。

---

## ADR-002: Flutter を採用する

**決定**: モバイルは Flutter（iOS / Android）。

**理由**:
- 「操作性・UI の美しさを重視」という要求に対し、自前描画エンジンによる
  両 OS 完全同一の見た目とアニメーション表現が有利
- オンデバイス OCR の `google_mlkit_text_recognition` が成熟しており、
  日本語を含む認識が安定している
- 好み分析のグラフ表現に `fl_chart` が使える
- `supabase_flutter` は Supabase 公式メンテナンス

**トレードオフ**: Edge Functions は TypeScript のため言語が 2 つになる。
ただし v1 の Edge Function は分析バッチとリンク解決程度で軽量。

**却下した選択肢**: React Native (Expo) — TypeScript 統一の利点はあるが、
上記 3 点で Flutter が優位と判断。

---

## ADR-003: Supabase を採用する

**決定**: バックエンドは Supabase（PostgreSQL / Auth / Storage / Edge Functions）。

**理由**: 好み分析は「香水 × 香料 × 評価」の交差集計が中心であり、
リレーショナル DB が本質的に適している。Firestore のような NoSQL では
この集計が著しく書きにくい。認証・ストレージ・関数実行が一体で提供される点も採用理由。

---

## ADR-004: 評価スケールは 1.0〜5.0 の 0.1 刻み

**決定**: 総合評価は 1.0〜5.0 の 0.1 刻み。持続時間・拡散力は 1〜5 の整数。

**入力 UX**: 星をタップすると整数値が即入力され、そのまま横にドラッグすると
0.1 刻みで微調整できる。店頭での高速入力（タップ 1 回）と分析解像度を両立させる。

**理由**: 0.5 刻みでは好み分析の解像度が不足する一方、
0.1 刻みの入力を必須にすると店頭での記録速度が落ちる。両立させる UX で解決する。

---

## ADR-005: 試香ログの「時間経過ごとの個別メモ」は v1 では実装しない

**決定**: ユーザーが時間経過（トップ／ミドル／ラスト）ごとに個別のメモを残す機能は v1 のスコープ外。

**注意**: 香水マスタ側のノートピラミッド情報（トップ／ミドル／ラストの香料構成）は
好み分析の中核であり、**v1 に含む**。見送るのはユーザーによる段階別記録のみ。

**将来の追加方法**: `tasting_log_phases (log_id, phase, elapsed_minutes, memo, rating)` を新設する。

## ADR-006: 香水 DB はスクレイピングで初期構築する

**決定**: スクレイピングによる初期構築 ＋ ユーザー投稿による継続的拡充。

**理由**: 香水データの商用 API は選択肢が乏しく、
自前 DB を持たなければ好み分析というコア価値が成立しないため。

**実装上の必須要件**（[data-ingestion.md](data-ingestion.md) 参照）:
robots.txt の尊重、各ソースの利用規約の事前確認、レート制限（1 req / 2 秒）、
識別可能な User-Agent、事実データのみの取得（レビュー本文・画像は取得しない）、
`source_url` による出典保持、ソース差し替え可能なアダプタ設計。

国内 EC の価格・購入リンクについては、スクレイピングではなく
楽天ウェブサービス / Amazon PA-API といった公式 API を使う。

**リスク**: 特定ソースの利用が継続できなくなる可能性。
これに備え、ユーザー投稿と公式サイト由来のデータのみでも DB を維持できる状態を中期目標とする。

## ADR-007: ユーザー投稿は即時反映し、未検証フラグで品質を担保する

**決定**: ユーザーが登録した香水は即座に DB へ反映し、`is_verified = false` を付与する。
検索結果では検証済みを優先表示し、未検証はセクションを分けて表示する。

**理由**: 承認待ちにすると、投稿したユーザー自身がその場でログを残せず、
店頭での利用というコアユースケースが破綻するため。

**重複対策**: 投稿フォームでブランドと製品名を入力した時点であいまい一致候補を提示し、
「登録」より「既存を選ぶ」を選ばせる導線にする。事前抑止を最優先とする。

---

## ADR-008: 好み分析は説明可能な統計的手法を採用する

**決定**: 行列分解や埋め込みベースの手法ではなく、
ベイズ補正つきの統計集計とコサイン類似度によるコンテンツベース手法を採用する。

**理由**: 本アプリの核心価値は「自分の好みを客観化できること」であり、
その信頼性は推薦精度そのものよりも**判定根拠を提示できること**に依存する。
すべての判定について、根拠となったログへドリルダウンできる状態を維持する。

協調フィルタリングはユーザー数が十分に増えるまで機能しないため v2 以降。

---

## ADR-009: 「配合バランス問題」に共起ペアで対応する

**決定**: 「同じローズでも配合バランスによって好き嫌いが分かれる」という課題に対し、
香料単体・香調アコード・香料の共起ペアの 3 つを特徴量として併用する。

**理由**: 香料単体のスコアだけでは条件付きの嗜好を表現できない。
共起ペアを加えることで「ローズは好きだがローズ×ウードは苦手」を検出でき、
ユーザーに提示できる形になる。

**組み合わせ爆発の回避**: 共起 3 回以上かつ主要香料に限定し、
さらに「構成香料単体のスコアからの乖離」が閾値を超えるものだけを提示する。

## ADR-010: 収益化は導線と計測のみ v1 で実装する

**決定**: 購入導線とクリック計測を v1 で実装し、
アフィリエイト提携（ID の取得）は後回しにする。

**理由**: 提携審査には時間がかかり、アプリ公開との前後関係が読めないため。
リンクを URL テンプレート方式で保持し、`affiliate_id` が NULL でも動作するようにしておけば、
提携完了後に DB のレコードを更新するだけで有効化できる。

クリック計測を先に入れることで、提携交渉時の実績データにもなる。

---

## ADR-011: 多言語対応はスキーマのみ先行する

**決定**: v1 の UI は日本語のみ。ただしデータは `name_ja` / `name_en` の 2 カラムを持ち、
アプリ側は必ずロケール解決関数を経由してアクセスする。

**理由**: 3 言語目が必要になった時点で `*_translations` テーブルへ移行する際、
この規約を守っていれば変更がデータ層に閉じるため。
最初から翻訳テーブルを作るのは v1 の複雑度に見合わない。
