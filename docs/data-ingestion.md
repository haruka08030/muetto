# 香水マスタ DB の構築・運用方針

本プロジェクト最大のリスクは「香水製品データ（ブランド・ノート・香調）の量と質の確保」である。
本ドキュメントはその調達方法と、データ品質を維持する運用を定義する。

---

## 1. 方針

**スクレイピングによる初期構築 ＋ ユーザー投稿による継続的拡充。**

| 段階 | 手段 | 目的 |
|---|---|---|
| 初期構築 | クローラでの一括取得 → 正規化 → 投入 | v1 リリース時点で検索が成立する母数を確保 |
| 継続拡充 | ユーザー投稿（即時反映＋未検証フラグ） | ロングテール・新作・国内限定品を埋める |
| 定期更新 | 月次の再クロールで差分反映 | 新作の追加、情報の訂正 |

### 目標

| 指標 | v1 リリース時 |
|---|---|
| ブランド数 | 200 以上 |
| 香水製品数 | 5,000 以上 |
| ノート情報の充足率 | 製品の 80% 以上でトップ／ミドル／ラストが埋まっている |
| 香調アコードの充足率 | 製品の 70% 以上 |

母数より**充足率を優先**する。ノートが空の製品は好み分析に寄与せず、
検索結果を汚すだけなので、充足率の低いソースからの大量投入は避ける。

---

## 2. 取得時の前提と制約

スクレイピングによる構築はプロジェクトの方針として決定済み。
ただし実行にあたり、以下を**実装上の必須要件**とする。

1. **robots.txt を尊重する** — クローラは `robots.txt` を解釈し、Disallow のパスを取得しない
2. **各サイトの利用規約を事前に確認する** — 公開前に対象ソースごとの可否を確認し、
   本ドキュメントの「ソース一覧」に確認結果を記録する
3. **レート制限** — 1 ドメインあたり 1 リクエスト / 2 秒以上の間隔。並列度は 1
4. **識別可能な User-Agent** — 連絡先を含む UA を設定する
5. **取得対象は事実データに限定する** — ブランド名、製品名、発売年、賦香率、
   香料構成、香調といった事実の集合のみを取得する。
   レビュー本文・解説文などの創作的表現、および画像は取り込まない
   （製品画像はブランド公式素材またはユーザー投稿で賄う）
6. **出典を保持する** — 全レコードに `source_url` と `fetched_at` を記録し、
   問題が判明したソースを一括で切り離せるようにする
7. **ソース差し替え可能な設計** — 特定サイトへの依存を作らない。
   正規化後のスキーマを固定し、パーサはソースごとのアダプタとして分離する

> 将来、特定ソースの利用が継続できなくなった場合に備え、
> ユーザー投稿と公式サイト由来のデータで DB を維持できる状態を目指す。
> 「スクレイピング由来のデータがゼロになっても検索が成立する」ことを中期的な目標とする。

## 3. ソース一覧

| ソース種別 | 用途 | 規約確認 |
|---|---|---|
| 香水データベースサイト | ノート構成・香調・発売年・調香師 | **要確認（着手前に実施）** |
| ブランド公式サイト | 製品名・容量・賦香率・公式画像・公式ショップ URL | 要確認 |
| 国内 EC（楽天 / Amazon） | 容量・価格・JAN コード・購入リンク | **公式 API を優先**（楽天ウェブサービス、PA-API） |
| ユーザー投稿 | ロングテール・国内限定品 | — |

**国内 EC については、スクレイピングではなく公式 API を使う。**
楽天ウェブサービスと Amazon Product Advertising API はいずれも商品検索 API を提供しており、
アフィリエイト提携とも接続できるため、価格・購入リンクはこちらから取得する。

## 4. パイプライン設計

```
[1] Crawler (Python)
      │  ソースごとのアダプタ。robots.txt 準拠・レート制限・リトライ
      ▼
[2] Raw Store  (Supabase Storage / ingestion_sources.raw_payload)
      │  取得した生データをそのまま保存。content_hash で差分検知
      ▼
[3] Normalizer (Python)
      │  ブランド名・香料名・賦香率の正規化、日英対応辞書の適用
      ▼
[4] Staging Tables (staging_perfumes / staging_notes …)
      │  本番テーブルと同構造。ここで検証とレビューを行う
      ▼
[5] Merge  (SQL)
      │  名寄せキーで既存レコードと突き合わせ、upsert
      ▼
[6] Production Tables (perfumes / perfume_notes / perfume_accords)
```

**本番テーブルへ直接書き込まない。** 必ず staging を経由し、
件数・充足率・重複率のチェックを通過したものだけをマージする。

クローラと正規化は Python（`httpx` + `selectolax`）で実装し、
アプリ本体（Flutter / Supabase）とは独立したリポジトリ内ディレクトリ `tools/ingestion/` に置く。

## 5. 正規化ルール

### 5.1 ブランド名

- 全角→半角、大文字化、記号・空白の除去でスラグ化
- 別名辞書を持つ（例: `YSL` = `Yves Saint Laurent` = `イヴ・サンローラン`）
- 新規ブランドは自動作成せず、**未知ブランドとして人手確認のキューに積む**
  （表記ゆれによるブランドの重複増殖を防ぐ）

### 5.2 香水名

- 賦香率トークン（`Eau de Parfum`, `EDP`, `オードパルファム` 等）を名称から分離し、
  `concentration` カラムへ移す
- 名寄せキー: `brand_slug / name_slug / concentration`
- 「Intense」「Extreme」「Elixir」等のフランカーは**別製品として扱う**（香りが異なるため）

### 5.3 香料名（notes）

- 香料マスタは**あらかじめ人手で整備**する（推定 400〜600 語）。
  ここが分析の土台になるため、自動生成に任せない
- ソース側の香料名は日英対応辞書で `notes.id` へマッピング
- 辞書に無い香料は `unmapped_notes` に記録し、定期的に人手でマスタへ追加する
  （**未知の香料名で notes マスタを自動増殖させない**）

### 5.4 香調アコード（accords）

- カテゴリは固定リスト（20〜30 種）として定義し、増やさない
- ソース側のカテゴリ表現をマッピング表で固定リストへ寄せる

---

## 6. 差分更新

- `ingestion_sources.content_hash` で前回取得内容と比較し、変化がなければスキップ
- 変化があった場合、**検証済み（`is_verified = true`）レコードは自動上書きしない**。
  差分を `perfume_edit_suggestions` に積み、人手で判断する
- 未検証レコードは自動上書きしてよい

---

## 7. ユーザー投稿の品質管理

| 状態 | 挙動 |
|---|---|
| 投稿直後 | `is_verified = false`, `data_source = 'user'`。投稿者は即座に使える |
| 検索表示 | 検証済みを優先。未検証はセクションを分けて「未検証」バッジ付き |
| 重複疑い | 投稿時に名寄せキーで既存候補を提示し、「これですか？」と確認する（重複投稿の抑止） |
| 承認 | 管理者が確認して `is_verified = true` へ。v1 は Supabase Studio ＋ SQL で運用 |

**重複の事前抑止を最優先する。** 投稿フォームでブランドと製品名を入力した時点で
あいまい一致の候補をリアルタイム提示し、「登録」より「既存を選ぶ」を選ばせる導線にする。

---

## 8. 運用スケジュール

| 頻度 | 作業 |
|---|---|
| 月次 | 再クロール → staging → 差分レビュー → マージ |
| 週次 | `unmapped_notes` と未知ブランドキューの人手処理 |
| 週次 | ユーザー投稿の検証（`is_verified` の付与） |
| 随時 | 修正提案（`perfume_edit_suggestions`）の処理 |

v1 リリース直後は投稿量が読めないため、まず週次で運用し、
実際の投稿量に応じて頻度を調整する。
